# Decisions log

Judgment calls made while building, per phase, so they're visible rather than buried in code.

## Phase 1 — Foundation

- **Prisma 7, not 5/6.** `npm view prisma dist-tags` showed `latest` pointing at `8.0.0-rc.12`, an unreleased major. Pinned to `7.10.0`, the last tagged stable (`prev`), rather than building on a release candidate.
- **Driver adapter required.** Prisma 7 removed implicit URL-based connections — `PrismaClient` now requires an explicit driver adapter even for SQLite. Using `@prisma/adapter-better-sqlite3` + `better-sqlite3`. This also means the datasource URL used by the Prisma CLI (`prisma7.config.ts`, `file:./dev.db`) and the one read at runtime by the app (`src/lib/db.ts`, stripped of the `file:` prefix for the adapter) are two separate code paths reading the same env var — worth knowing if `DATABASE_URL` ever needs to change shape.
- **Prisma config file is `prisma7.config.ts`**, not `prisma.config.ts` — that's what `prisma init` generated for this version and what the CLI looks for. Not a typo.
- **Track points as a `Json` column on `Activity`/`Segment`/`Route`**, not a child table. Simplest thing that supports maps, charts, GPX export, and segment matching at prototype scale. A real-scale product would want a proper time-series table; flagged, not hidden.
- **Auth is hand-rolled**, per the brief: bcrypt password hashing, opaque random session tokens (SHA-256'd before storing, so a DB read alone can't be replayed as a cookie), `httpOnly`/`sameSite=lax` cookie, `Session` table with expiry. No NextAuth/Clerk/etc.
- **No `middleware`/`proxy.ts` gate.** Next.js 16 renamed `middleware.ts` to `proxy.ts` (still Node-runtime only, no edge). Rather than adopt a new, less-familiar API for a blanket auth gate, each protected page/Server Action calls `requireUserOrRedirect()` / `requireUser()` directly. More explicit per-route, easier to reason about which routes are actually protected when the API surface grows in later phases.
- **Mutations are Server Actions, not `/api` routes**, for anything that's really a form submission (auth, profile). `/api/*` Route Handlers are reserved for phases 2+ where a client component needs to fetch/mutate JSON directly (live recording tick updates, kudos toggle, etc.) — both paths call the same `requireUser()`/Prisma calls underneath, so authorization isn't duplicated logic, just a different transport.
- **Found and fixed during Phase 1 QA**: the initial `ProfileForm` (a Client Component) was given the full Prisma `User` object as a prop, including `passwordHash` (a bcrypt hash). Server Component → Client Component props are serialized into the page's RSC payload and shipped to the browser verbatim — so the hash was going out over the wire on every visit to `/settings/profile`, not just used in the UI. Fixed by introducing `PublicUser` (`Omit<User, "passwordHash">`) and a `toPublicUser()` helper in `src/lib/auth.ts`; every Server Component that hands a user into a "use client" component now passes `toPublicUser(user)`. Caught by an end-to-end smoke test (Playwright) that specifically greps the served HTML for `passwordHash`/bcrypt-hash patterns — kept as a standing regression check. **Rule going forward: the raw `User` type from `@/generated/prisma/client` never crosses into a Client Component prop — always `PublicUser`.**
- **Header avatar → `/settings/profile` link** added to the header (not in the original five-screen design mockup, which had no settings entry point in its nav). Necessary so there's a way to reach account settings at all; noted here since it's a deviation from the visual reference.
- **Seed script is users-only in Phase 1** (4 named demo users, shared password `password123`), matching the brief's phased build-up. Full ~8-user/3-month activity seed lands in Phase 2 once the `Activity` model has real write paths to generate realistic data through.
- **Units toggle stores per-user metric/imperial preference**; every distance/time/pace/elevation display funnels through `src/lib/units.ts` rather than being computed inline anywhere — required so unit correctness (the brief's explicit quality bar) has one place to get right and test.

## Phase 2 — Activity recording & detail

- **Tracks stored as `Json`** (confirmed from Phase 1's schema decision): a `TrackPoint[]` with `{lat, lng, ele, t, distM}`, cumulative distance computed once via `buildTrack()` and reused everywhere (stats, splits, charts, map) rather than recomputed per view.
- **Moving time is a speed threshold, not GPS-provided.** `computeTrackStats()` excludes any inter-point interval where speed drops below 0.5 m/s (stopped at a light, tying a shoe) from "moving time." Elapsed time is just first-to-last timestamp. This is the same convention Strava/Garmin use, and it's why moving time and elapsed time are shown as two separate stats.
- **Elevation gain smooths GPS altitude noise** with a 2m threshold before summing upward deltas — unsmoothed GPS altitude wildly overstates gain (see `elevationGainFromTrack` in `src/lib/geo.ts`). Still not as accurate as barometric-sensor data a real device would provide.
- **Effort score and calorie estimate are documented heuristics, not physiology.** `src/lib/effort.ts` weights moving-minutes by a per-sport intensity multiplier plus a small elevation bonus — there's no heart-rate data to build a real TRIMP score from. Calories are a flat MET-like per-minute rate per sport, not personalized to body weight. Both exist because Phase 6 (training dashboard, PRs, fitness/form) needs *some* comparable load number across activities — the weights themselves are a judgment call, called out here rather than presented as authoritative.
- **Live recording's Geolocation altitude is frequently null** (no barometric sensor on most laptops/some phones via the browser API) — falls back to `0`, which means elevation gain for live-recorded activities can read low/flat compared to the same route recorded on a real GPS watch. Manual entry and GPX/TCX upload aren't affected (uploaded files usually carry real barometric elevation).
- **Live recording calls a Server Action directly as a function**, not via a `<form>` — `createLiveActivityAction(points)` is invoked from client JS once the athlete taps Finish, since the payload (a live-captured points array) isn't naturally a form submission. Manual entry and GPX/TCX upload *do* use `<form action={...}>` for standard progressive enhancement.
- **Server Actions' default 1MB body limit was raised to 10MB** (`next.config.ts`) — a multi-hour recording's point array, or a longer GPX file, routinely exceeds 1MB.
- **Map provider (OpenFreeMap) is unreachable from this dev sandbox** (network policy blocks the tile host) — confirmed via `curl`, not a code defect. The map component fails open: a blocked tile fetch shows a blank map area and logs a console error, it doesn't crash the page or block stats/charts/splits from rendering. Untestable *in this sandbox specifically*; will need a real network check post-handoff.
- **"followers" privacy is temporarily owner-only.** `canViewActivity()` can't resolve the Follow graph before it exists (Phase 3), so `privacy: "followers"` currently behaves like `only_me` for everyone but the owner — the conservative direction, not the permissive one. Revisited when Follow lands, and audited for real in Phase 8.
- **Feed page is still a placeholder**, but now lists the signed-in user's own activities (instead of just a "coming soon" message) so activity creation/detail/edit has somewhere to navigate to and from before Phase 3's real feed exists. Replaced, not removed, when the social feed lands.
- **Chart colors are brand hex constants, not CSS custom properties** (`src/lib/chart-colors.ts`) — Recharts sets `stroke`/`fill` as SVG attributes, and `var(...)` doesn't resolve reliably there. Grid/axis lines use `stroke="currentColor"` instead, inheriting a Tailwind `text-*` color utility from a wrapper element, which *does* stay theme-aware.
- **Ran the dataviz skill's palette validator** on the two-line fitness/form chart's originally-planned colors (brand blue + brand bright-blue): it hard-fails the normal-vision distinguishability check (ΔE 10, below the 15 floor) — the two blues are genuinely too close for anyone to tell apart by color, dash pattern or not. That chart isn't built until Phase 6, but noting the fix now: pair the accent blue (primary metric) with a neutral gray (de-emphasized comparison line) instead of a second blue, since Pulse's own brand rule ("blue means action or data; if a screen reads as mostly blue, it's wrong") already argues against two blues as competing peers anyway.

## Phase 3 — Feed & social

- **"followers" privacy is now real**, resolved against the actual `Follow` graph (`src/lib/social.ts`'s `canViewActivity`) — the Phase 1/2 owner-only placeholder is gone. Still not the full Phase 8 audit (that pass checks every read path, not just this one function).
- **Feed query is a single `OR`**: own activities (any privacy) plus followed athletes' `everyone`/`followers` activities, ordered by `startedAt`. No pagination yet — capped at 30 rows, which is fine at seed-data scale; flagged for whenever real usage needs infinite scroll.
- **Feed thumbnails are server-rendered SVG, not a map.** A MapLibre instance per feed card (each with its own tile fetches) would be far too heavy for a scrolling list. `src/lib/route-thumbnail.ts` projects a track's lat/lng into a small local-equirectangular SVG path instead — same visual idea as the design mockup's abstract route squiggle, but computed from the real track rather than decorative.
- **Comment threading is one level deep** — a reply to a reply collapses onto the original top-level comment (`buildCommentTree` in `src/lib/comments.ts`) rather than growing infinitely nested. Matches how most feed UIs actually present threads and keeps the UI simple.
- **Kudos/follow are optimistic-UI client actions** (`toggleKudosAction`, `toggleFollowAction`) called directly as functions from client components, not via `<form>` — same pattern as Phase 2's live-recording finish. The client flips its local state immediately and rolls back only if the server call returns an error, so taps feel instant.
- **Athlete profile activity list re-derives privacy filtering inline** (`OR: [{privacy: everyone}, ...])`) rather than calling `canViewActivity` per row — same rule, just batched into one query instead of N. Kept in sync manually since it's a small, self-contained page; if this logic needs to appear a third place, it should move into a shared query builder instead of copy-pasting again.
- **Feed page's "empty" copy changed** from Phase 2's placeholder to a real empty state ("your feed is quiet, follow someone or log your own") — the Phase 2 smoke test that checked for the old placeholder text was updated to match, not silently left broken.

## Phase 4 — Segments

- **Matching is nearest-vertex, not true point-to-polyline projection.** `src/lib/segment-matching.ts` walks an activity's track looking for a run of points that stays within a 40m corridor of the *nearest segment vertex* at each step, with "nearest vertex index only increasing" standing in for a direction check (segment points are stored start→end). This is a documented approximation, not exact geometry — it can be slightly off on sparse tracks or tight switchbacks, and only the *first* qualifying pass through a segment in a given activity is matched (an out-and-back covering it twice only records one direction). A 500m bounding pre-filter on the segment's start point avoids running the full matcher against every segment in the database for every new activity.
- **Creating a segment gives its source activity the founding effort automatically.** Caught this gap while testing: the activity a segment is carved from obviously covers it, but the original `createSegmentFromActivity` only created the `Segment` row, not a `SegmentEffort` for the activity that produced it — so the segment creator was absent from their own segment's leaderboard until they happened to run it again. Fixed by creating that founding effort (marked PR) as part of segment creation itself, and caught by the Phase 4 smoke test asserting the source activity lists its own new segment.
- **Segment range selection re-derives everything server-side.** The client-side range-picker (`SegmentRangeForm`) computes a live distance/elevation preview from the track for UI feedback, but only sends `startIndex`/`endIndex` to the server action — `createSegmentFromActivity` re-slices the canonical `activity.points` itself rather than trusting any client-computed geometry.
- **Leaderboard privacy is enforced per effort**, not assumed open: `getSegmentLeaderboard` filters every effort through the same `canViewActivity` check as everywhere else, based on the effort's underlying activity's owner/privacy — an effort from a private activity doesn't appear on the public leaderboard just because it happened to match a public segment.
- **Seed data fabricates non-source segment efforts directly**, rather than relying on the real matcher. Independently-randomized synthetic loop tracks (see Phase 2's `synthesizeLoopTrack`) never actually retrace the same ground twice, so the matcher would legitimately find nothing between two different seeded users. Segments are still created through the real `createSegmentFromActivity` path (one per represented sport, carved from a real track); only the *other* athletes' efforts on that segment are inserted directly, so the leaderboard has real-looking ranked data without pretending the geometry-based matcher succeeded where it structurally couldn't.
- **Explore is now a real segment directory** (was a Phase 1 "coming soon" stub) — lists all segments with effort counts, sorted newest-first. No search/nearby yet (would need real geospatial querying); flagged as a possible later addition, not committed to a phase.

## Phase 5 — Routes

- **No elevation API is wired up for hand-drawn routes.** Clicking waypoints on a map gives lat/lng only — there's no elevation at a point without a lookup service, and adding one (even a free one) means a new external dependency with its own reliability/rate-limit questions, which felt like scope creep for a route *planning* tool where the primary value is the line and distance, not the profile. Hand-drawn routes report `elevationGainM: 0`, clearly, rather than a fabricated number. (Routes saved from an existing tracked activity's real points, as the seed data does, DO have real elevation gain — the gap is specifically GPS-free hand-drawn routes.) A real elevation provider is a reasonable follow-up if routes become a bigger part of the product.
- **GPX export uses `<rte>`/`<rtept>` (a planned route), not `<trk>`/`<trkpt>`** (a recorded track) — routes have no timestamps, so the track element type would be semantically wrong. A Route Handler serves it (`/routes/[id]/gpx`) with `Content-Disposition: attachment`, auth-checked the same as every other user-data endpoint (401 on `AuthError` rather than an unhandled 500, since Route Handlers — unlike pages — don't get to redirect to `/login`).
- **Route builder sends only waypoint indices' worth of client computation, never trusts client geometry for the saved record** — same pattern as Phase 4's segment range picker. The live distance/elevation shown while building is for UI feedback only; `createRouteAction` re-derives distance from the submitted points server-side via the same `buildTrack`/`geo.ts` helpers used everywhere else.
- **Fixed a map attribution inconsistency while building this**: `ActivityMap` had `attributionControl: false` (removing MapLibre's default attribution badge) while the new `RouteBuilderMap` didn't. Rather than turning it off in both places, turned it *on* in `ActivityMap` — OpenFreeMap's attribution requirement was never actually verified, so defaulting to "leave it showing" is the safer assumption than "assume it's fine to hide."
- **Routes has no tab-bar slot** — the five-tab bar (Feed/Explore/Record/Groups/You) is fixed by the original design brief and doesn't have room for a sixth destination. Added a "ROUTES" quick-action link on the feed instead, alongside "+ LOG AN ACTIVITY". Worth a look in Phase 6 once the "You" dashboard exists as a real page — that's arguably a more natural home for "my saved routes" than the feed.

## Phase 6 — Training dashboard

- **Fitness/form uses the standard CTL/ATL/TSB model**, not an invented one: CTL (fitness) is a 42-day EWMA of daily total effort score, ATL a 7-day EWMA of the same signal, and form (TSB) is *yesterday's* CTL minus yesterday's ATL — today's training hasn't counted toward fitness yet, which is why the two lines don't converge on "today." The EWMA warms up from the athlete's actual first activity, not just the displayed 12-week window, so the chart's start isn't an artificially-low cold start. This all rides on Phase 2's `effortScore` heuristic, so it inherits that heuristic's caveats (documented there).
- **Applied the Phase 2 dataviz finding for real**: the fitness/form chart pairs accent blue (Fitness, the primary metric) with a neutral gray dashed line (Form, de-emphasized context) instead of the two brand blues, which fail the palette validator's distinguishability check. See `FitnessFormChart.tsx`.
- **Training-log calendar shading is per-athlete relative, not an absolute scale.** "Hard" for someone running 20km/week looks different from "hard" for someone running 80km/week — the 4 non-zero shading levels are quartile thresholds computed from that athlete's *own* days with any training, not a fixed effort-score cutoff shared across users.
- **Personal records are approximated from whole-activity totals**, not a true "best 5K anywhere inside any activity" sliding-window search (a much harder problem, in the same family as segment matching but over arbitrary distances rather than a fixed course). An activity counts toward a distance PR (1K/5K/10K/Half/Marathon) if its total distance is within ±5% of that target; the fastest overall time among matches is the "PR." Good for races and planned-distance runs, not for a PR set mid-way through a longer run. Ride PRs (longest ride, biggest climb) are exact — those really are just max-over-activities.
- **Goals recur every period rather than being one-off**: a "weekly" goal's progress is always computed against the calendar week (Monday–Sunday) containing today, a "monthly" goal against the current calendar month — not a fixed window starting from when the goal was created. `startDate` exists so a goal can be scheduled to start in the future, not to anchor its recurrence window.
- **Caught and fixed a real narrow-viewport layout bug while testing**: the "this week"/"this month" cards' three mini-stats (time/elevation/sessions) used `flex` with a fixed gap, which measurably overflowed its container at 390px width (confirmed via `scrollWidth` vs `clientWidth`, not just eyeballing). Switched to a `grid grid-cols-3` layout with `min-w-0`/`truncate` on each cell, which degrades to an ellipsis on genuinely-too-long values instead of pushing the layout wide. Worth remembering for any other multi-stat row: `flex` + `gap` doesn't shrink below content size on its own, `grid-cols-N` does.
- **Dashboard is the more natural home for "my saved routes" than the feed** (flagged in Phase 5) — not moved yet, since the feed placement still works; worth revisiting if the feed gets crowded.

## Phase 7 — Clubs & challenges

- **Challenges belong to a club** (created from within a club page) rather than also supporting freestanding challenges, even though the schema's `clubId` is nullable. Keeps "clubs and challenges" as one cohesive feature area per the brief's phase grouping instead of two half-built ones; a standalone challenges directory is a reasonable follow-up if it's ever wanted.
- **Found and fixed a real scoping bug while testing**: a "100km of running" challenge in a running club was actually summing *every* participant's total distance across all sports — a cyclist member showed 392mi against a 62mi target because his rides counted too. `Challenge` had no sport field at all. Added `sportType` to the model (migration `add-challenge-sport`), inherited automatically from the club's sport when a challenge is created (no extra form field needed — a challenge belongs to its club's context), and threaded through `getChallengeLeaderboard`'s activity query. Confirmed by screenshot before/after: the same cyclist correctly shows 0mi once the challenge only counts runs.
- **Club leaderboard is scoped to the club's sport the same way**, and was designed that way from the start (`getClubLeaderboard` in `src/lib/clubs.ts`) — the challenge gap above was specifically that *challenges* hadn't inherited the same scoping the club leaderboard already had.
- **Club/challenge leaderboards show distance in the *viewer's* unit preference**, same convention as every other leaderboard in the app — not the club's or other members' preferences. A club with mixed metric/imperial members will show everyone's distance in whichever unit the person looking at the page uses.
- **The club owner can't leave their own club** (`toggleClubMembershipAction` rejects it) — there's no ownership-transfer or club-deletion flow yet, so an ownerless club would be an orphaned dead end. Flagged, not solved.

## Phase 8 — Privacy pass & QA

- **Privacy zones clip only the map, never stats/splits/elevation.** `src/lib/privacy.ts`'s `clipTrackToZones` strips leading/trailing track points that fall within any of the owner's saved zones (home, work, wherever) before the track ever reaches `ActivityMap` — for the feed thumbnail (`src/app/page.tsx`) and the activity detail map (`src/app/activities/[id]/page.tsx`) alike. Splits, the elevation-profile chart, and aggregate stats stay based on the *full*, un-clipped track: they're distance-indexed numbers, not raw coordinates, so there's nothing to leak, and clipping them too would just make an athlete's own stats look wrong to their own followers for no privacy benefit. The owner's own view of their own activity is never clipped, regardless of their zones — only other viewers get the trimmed track.
- **Clipping happens server-side, before the points ever reach a Client Component prop**, not as a CSS/JS hide on an already-rendered map — the same "never trust the browser with what shouldn't be sent" principle as the Phase 1 `passwordHash` fix. Verified directly (not just via the UI) with a Playwright smoke test that fetches the raw activity-detail and feed HTML as a non-owner and asserts the exact zoned coordinate is byte-absent from the response, in addition to checking the UI placeholder — the brief's "must never leak through the API, not just the UI" is checked at the HTTP-response level, not just by looking at the rendered page.
- **When the entire track sits inside a zone** (e.g. a short warm-up loop that never leaves home), `clipTrackToZones` legitimately returns an empty array — the activity detail page shows a "Route hidden near start/end" placeholder instead of an empty/broken map in that case, while stats and splits still render normally.
- **Audited every other place raw lat/lng ever reaches a page** (grepped for every `ActivityMap`/`points=` usage): `/record` (always the signed-in user's own in-progress recording), `/routes/new` (same, still being built), and `/routes/[id]` (routes are owner-only — `route.userId !== user.id` → `notFound()`, enforced both on the page and on the `/routes/[id]/gpx` export route). `/activities/[id]` and the feed are the *only* two places another user's raw coordinates were ever reachable, and both now go through `getViewableTrack`/`clipTrackToZones`. No other read path needed changes.
- **Segment thumbnails can't leak a zone even without explicit clipping.** A segment created from a range that happens to include a zoned start/end would carry the real coordinates in `segment.points`, but the segment detail page (`src/app/segments/[id]/page.tsx`) only ever turns those points into a *relative*, bounding-box-normalized SVG shape via `trackToSvgPath` — computed server-side, with only the resulting shape string (no absolute lat/lng) ever reaching the page. Segment creation is also owner-only to begin with. Left unclipped deliberately, since there's genuinely nothing to clip: the absolute coordinates never reach any client-visible output for that page.
- **Full per-activity visibility audit**: re-confirmed `canViewActivity` (owner → true, `everyone` → true, `only_me` → false, `followers` → real follow-graph check) is the single gate used by the activity detail page, the feed query, the athlete-profile activity list (inlined as an equivalent `OR`, per the Phase 3 note already on record), and segment-effort visibility on leaderboards. No read path was found bypassing it.
- **Added root `error.tsx` and `not-found.tsx` boundaries** — neither existed through Phase 7, so an unhandled exception or a bad `/activities/<garbage-id>` URL fell through to Next's default (unstyled) error/404 pages instead of Pulse's own chrome. Both are minimal by design (no data fetching, so they can't themselves fail) and offer a way back to the feed.
- **Demo-deploy scaffolding for a throwaway preview link** (added after Phase 8 closed, at the user's request for "a link to the app"): `web/vercel.json`'s `buildCommand` runs `prisma migrate deploy` + `prisma db seed` at build time into `prisma/build-seed.db`, which `next.config.ts`'s `outputFileTracingIncludes` (needed since nothing imports that file, so Next's tracer wouldn't otherwise bundle it) pulls into the deployed function output; `src/lib/db.ts`'s `resolveDbPath` then copies it into `/tmp` on cold start, since Vercel's deployment bundle is read-only outside `/tmp`, so writes need a real writable location. All of this is a no-op unless `process.env.VERCEL` is set — local dev is untouched. This is explicitly **not** the real persistence story: writes vanish on the next cold start and aren't shared across concurrent instances. It exists purely so a `*.vercel.app` link has something to click through with realistic seeded data; the README's "Deploying" section (Postgres + a real driver adapter) is still the actual recommended path for anything meant to stay up.
- **Found and fixed a real bug in that scaffolding**: login itself was broken, not just flaky writes. Every request can land on a different serverless instance, each with its own isolated `/tmp` SQLite copy — so a `Session` row written by the instance that handled the login POST was invisible to whichever instance handled the very next request, making it look like login silently failed (both for the seeded demo accounts and for a freshly signed-up one). Fixed for the seeded accounts by making `src/lib/auth.ts`'s demo-deploy path (again gated on `process.env.VERCEL`) skip the `Session` table entirely: the cookie is a self-verifying HMAC-signed `userId` checked directly against the `User` table, which — unlike a session row — is baked identically into every instance's copy. A hardcoded demo secret is fine here since this path only ever runs against a throwaway public preview with published demo credentials, never a real deploy. Signing up a *new* account on the demo deploy still won't reliably work (that user row itself only exists on whichever one instance created it) — flagged as a known remaining limitation of the demo link, not something worth solving short of the real Postgres path.
- **Removed the login barrier on the demo deploy, at the user's request**: `src/app/demo-login/route.ts` (demo-only, no-ops back to `/login` off Vercel) transparently logs a visitor in as the seeded `jonas@example.com` account and redirects to `/`; `requireUserOrRedirect()` now sends unauthenticated visitors there instead of `/login` when `process.env.VERCEL` is set. `/login`/`/signup` are untouched and still reachable directly for anyone who wants to switch to a different seeded account.
- **Found and fixed a real bug in `demo-login`**: it initially returned `NextResponse.redirect(...)` after calling `createSession()` (which sets the cookie via `next/headers`'s `cookies().set()`), and that combination doesn't reliably carry the `Set-Cookie` header — every visit to `/` looked unauthenticated again and bounced straight back to `/demo-login`, an infinite redirect loop (`ERR_TOO_MANY_REDIRECTS`) the user hit directly on the live deploy. Fixed by switching to `redirect()` from `next/navigation` (the same helper `requireUserOrRedirect` and every Server Action in this codebase already use after `createSession()`), which composes correctly with `cookies().set()` since both go through Next's own internal response machinery instead of a manually-constructed `NextResponse`. Verified locally by running the dev server with `VERCEL=1` and a real `prisma/build-seed.db` snapshot, then curling `/` and `/dashboard` with a fresh cookie jar and confirming a 200 with no loop, rather than just reasoning about it — the earlier `NextResponse.redirect` version looked correct on inspection, which is exactly why it needed an actual run to catch.
- **Vitest added for the "genuinely tricky logic" the brief calls out by name**, and nothing else — no UI/component tests, per the brief's explicit instruction. Six files, 53 tests: `geo.test.ts` (haversine, cumulative distance, elevation-gain noise threshold, moving-time-vs-elapsed, splits, downsampling), `units.test.ts` (metric/imperial conversions, pace/speed/duration formatting), `gpx.test.ts` / `tcx.test.ts` (happy path plus malformed/empty-file error cases for both upload formats), `segment-matching.test.ts` (a track that matches a segment, one that strays outside the corridor mid-way, one run in the wrong direction, one that never comes near it), and `privacy.test.ts` (clipping the start only, the end only, both, no zones, a zone that doesn't touch the middle of the track, and the whole-track-inside-a-zone edge case). Runs via `npm run test`.
- **Replaced the whole SQLite-on-serverless workaround with real Postgres**, after it kept producing new bugs (per-instance `/tmp` isolation breaking sessions, then a redirect-loop bug in the fix for that). The user provisioned a free Prisma Postgres database directly (I couldn't reach `api.prisma.io` or any raw Postgres TCP connection from this sandbox — organization network policy blocks both; confirmed via the sandbox's own proxy-status diagnostics rather than assumed) and gave me the direct connection string. Swapped `prisma/schema.prisma`'s `datasource.provider` to `postgresql` (the schema was deliberately kept Postgres-compatible from Phase 1 — no SQLite-only features — so this needed no model changes) and `src/lib/db.ts`'s adapter from `@prisma/adapter-better-sqlite3` to `@prisma/adapter-pg`. Regenerated `prisma/migrations` from scratch for Postgres via `prisma migrate diff --from-empty --to-schema` (works entirely offline — no live DB connection needed to generate migration SQL, only to apply it). Removed everything the workaround needed and Postgres doesn't: `resolveDbPath`'s `/tmp` copy logic, `next.config.ts`'s `outputFileTracingIncludes` for the bundled snapshot, and `auth.ts`'s demo-only signed-cookie session bypass (real `Session` rows now work reliably everywhere, since Postgres — unlike per-instance SQLite — is one shared database). `vercel.json`'s `buildCommand` now runs `prisma migrate deploy && prisma db seed` against the real `DATABASE_URL` on every build, which — unlike everything in this list above it — actually happens on Vercel's own build machine, not this sandbox, since that's the only environment in this loop with real internet access. The `/demo-login` auto-login route (the user's explicit "remove the password barrier" ask) is unchanged in behavior, just simpler now that it rides on ordinary DB-backed sessions instead of a special-cased signed cookie.
